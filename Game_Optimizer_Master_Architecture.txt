GAME PERFORMANCE OPTIMIZER C++
MASTER ARCHITECTURE / DESIGN SPECIFICATION
============================================

PURPOSE
-------
Build an Adaptive Windows/Game Performance Optimizer.

Primary goal:
- Reduce stutter.
- Improve frame-time stability.
- Reduce input latency where possible.
- Reduce CPU/GPU/system contention.
- Reduce unnecessary background interference.
- Improve consistency of the Windows/game environment.
- Adapt optimization to the actual hardware, Windows state, game, workload,
  and measured behavior.

FPS IS NOT THE PRIMARY OBJECTIVE.
FPS may be measured, but it is not the sole or primary decision metric.

IMPORTANT PROJECT DIVISION
--------------------------
THIS CONVERSATION:
- Collect and organize optimization techniques.
- Evaluate technical mechanisms.
- Build the Master Technique List.
- Build the architecture, dependencies, conflicts, verification methods,
  and adaptive rules.

OTHER DATA/EVIDENCE CONVERSATION:
- Collect real-world benchmarks.
- Collect experiments.
- Collect before/after measurements.
- Collect hardware/game/Windows conditions.
- Collect positive and negative results.

FINAL PROCESS:
TECHNIQUE INVENTORY
+
REAL-WORLD DATA
+
MICROSOFT / TECHNICAL DOCUMENTATION
→ CROSS-CHECK

→ DEPENDENCY / CONFLICT ANALYSIS
→ ADAPTIVE RULES
→ FINAL TECHNIQUE DATABASE
→ IMPLEMENTATION
→ VERIFICATION

4. TECHNIQUE SELECTOR
============================================================

The selector chooses techniques based on:

- Hardware.
- Windows version/build.
- CPU topology.
- GPU.
- RAM.
- Storage.
- Network.
- Power state.
- Laptop/desktop.
- Game.
- Game API.
- Game process tree.
- Current bottleneck.
- Current background load.
- Existing Windows settings.
- Evidence level.
- Dependencies.
- Conflicts.
- Risk.
- Previous measured results.

Example:

CPU contention HIGH
+ hybrid CPU
+ AC power
+ background load HIGH

→ CPU/process/power/background candidates.

GPU saturation HIGH
+ CPU contention LOW

→ do NOT blindly apply CPU tweaks.

The selector must choose only relevant candidates.


============================================================
5. DEPENDENCY / CONFLICT ENGINE
============================================================

Before APPLY:

- Does technique require another technique?
- Does it conflict with another technique?
- Is it compatible with this Windows version?
- Is it compatible with this CPU?
- Is it compatible with this GPU?
- Is it compatible with this game?
- Is it compatible with this API?
- Is it compatible with anti-cheat?
- Does another technique already control the same setting?
- Is the setting already at the requested state?
- Can it be safely restored?

Example:
CPU affinity and CPU Sets must not be treated as independent blind tweaks.

Every technique should have:
- Dependencies.
- Conflicts.
- Preconditions.
- Postconditions.

============================================================
8. VERIFY ENGINE
============================================================

Verification must check the REAL resulting state.

Example:

Requested:
CPU Priority = HIGH

Verify:
Actual process priority = HIGH

Requested:
Power setting = X

Verify:
Actual power setting = X

Requested:
Affinity = selected CPU set

Verify:
Actual affinity/CPU set = selected value

If verification fails:
- Mark application failed.
- Do not assume success.
- Roll back when appropriate.


============================================================
9. KEEP / ROLLBACK ENGINE
============================================================

BEFORE
  ↓
APPLY
  ↓
VERIFY
  ↓
MEASURE AFTER
  ↓
COMPARE

KEEP if:
- Target metric improves.
- No significant regression.
- System remains stable.
- Compatibility remains acceptable.
- Result is consistent enough for the relevant condition.

ROLLBACK if:
- No useful improvement.
- Target metric becomes worse.
- Stutter increases.
- Input latency increases.
- System responsiveness degrades.
- Stability/compatibility becomes worse.
- Verification fails.
- A conflict appears.

The decision must be based on measured results, not assumptions.


============================================================
10. SESSION STATE ENGINE
============================================================

While game is running:

MONITOR
→ DETECT STATE CHANGE
→ RE-DIAGNOSE
→ RE-EVALUATE TECHNIQUES
→ ADJUST ONLY WHEN JUSTIFIED
→ VERIFY
→ MEASURE

When game exits:

GAME EXIT
→ RESTORE TEMPORARY CHANGES
→ VERIFY RESTORE
→ SAVE SESSION RESULT

============================================================
12. MASTER TECHNIQUE EVALUATION STATUS
============================================================

A — CORE / STRONG FOUNDATION
- Required or strongly justified system infrastructure.
- Detection.
- Measurement.
- Verification.
- Backup.
- Rollback.
- Adaptive selection.
- Hardware awareness.
- Game detection.
- Session management.

B — CONDITIONAL
- Useful under specific conditions.
- Must be selected adaptively.
- Requires compatibility/evidence checks.

C — EXPERIMENTAL
- Technical mechanism exists or implementations exist.
- Evidence is insufficient or behavior is highly workload-dependent.
- Never blindly enable by default.

D — LOW PRIORITY / REJECT CANDIDATE
- Weak justification.
- High downside relative to expected value.
- No meaningful measured benefit.
- Or better alternatives exist.

IMPORTANT:
This status is an engineering evaluation layer.
Final classification must be updated after cross-checking REAL-WORLD DATA.

============================================================
15. EVIDENCE MODEL
============================================================

Evidence levels:

LEVEL 1:
Microsoft / official technical documentation.

LEVEL 2:
Working open-source or documented implementation.

LEVEL 3:
Independent benchmark / controlled experiment.

LEVEL 4:
Repeated real-world measurements.

LEVEL 5:
Community reports / anecdotal claims.

IMPORTANT:
A technique being present in a popular optimizer does NOT prove that it improves performance.

A technique being technically valid does NOT prove that it improves every game.

A technique must be evaluated in the conditions where it is intended to operate.

============================================================
21. IMPORTANT RULES
============================================================

RULE 1:
Do not optimize blindly.

RULE 2:
Do not assume FPS is the only objective.

RULE 3:
Do not treat a successful API call as proof of performance improvement.

RULE 4:
Measure before and after.

RULE 5:
Verify actual system state.

RULE 6:
Back up reversible state.

RULE 7:
Rollback when the result is negative.

RULE 8:
Do not apply the same technique to every hardware/game configuration.

RULE 9:
Respect dependencies and conflicts.

RULE 10:
Treat High/Realtime priority as conditional/experimental, not universal.

RULE 11:
Treat aggressive Windows debloat as conditional, not universal.

RULE 12:
Treat driver/BIOS/GPU clock modifications as experimental.

RULE 13:
Use official documentation to understand mechanisms.

RULE 14:
Use real-world data to determine practical effectiveness.

RULE 15:
Use measured results to refine future selections.

RULE 16:
Temporary game-session changes should be restored after the game exits.

RULE 17:
The optimizer must be able to detect when a previous setting has been
reverted or changed externally.

RULE 18:
The final optimizer should be adaptive rather than a static tweak list.

The finished product should function as:

DETECTION
→ DIAGNOSIS
→ MEASUREMENT
→ TECHNIQUE SELECTION
→ DEPENDENCY / CONFLICT CHECK
→ BACKUP
→ APPLY
→ VERIFY
→ MEASURE
→ KEEP / ROLLBACK
→ SESSION STATE UPDATE
→ CONTINUOUS MONITORING
→ RESTORE

The core idea:

DO NOT ASK:
"Which gaming tweaks should we apply?"

ASK:
"What is happening on this machine, in this game, right now,
and which technically supported, evidence-backed technique is
appropriate for this exact condition?"

END OF MASTER DESIGN SPECIFICATION
